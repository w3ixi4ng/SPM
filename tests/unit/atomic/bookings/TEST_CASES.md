# Test cases — bookings service (unit)

Covers `tests/unit/atomic/bookings/test_app.py`: the atomic service that owns
venue booking requests (`bookings.bookings`). It stores and lists them and
nothing else; update and delete wait for a story that needs them. It never
calls another service, and it never judges whether a request is suitable.
The `venue_bookings` composite does that before it writes here. Supabase is
replaced with a `MagicMock` through `app.dependency_overrides[get_db]`, so
there is no network, database, or Docker.

There are no browser routes. Kong has no entry for this service, and its only
caller is the `venue_bookings` composite inside the Docker network, the same
arrangement as the events service's `/internal` routes. So there is no
session or role check here, and none is tested.

## TC-BOOKINGS-002 — a booking is stored as pending, with the submission time set by the service

- **Scenario:** A complete booking is saved as `pending`, and the service
  alone sets `status` and `submitted_at`.
- **Pre-conditions:** The fake's insert returns the inserted row plus `id`
  and `submitted_at`.
- **Steps:** `POST /bookings` with the shared body.
- **Test data:** Shared body.
- **Expected:** `201`. The response carries every shared field plus `id`,
  `status: "pending"` and a non-null `submitted_at`. The values sent to
  `.schema("bookings").table("bookings").insert()` are the shared body plus
  `status="pending"` and an ISO-8601 `submitted_at` generated by the service.
- **Actual:** As expected.
- **Status:** Pass
- **Evidence:** `test_app.py::test_a_booking_is_stored_as_pending_with_a_service_set_submission_time`
